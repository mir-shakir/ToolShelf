    What is Unix epoch time?

    Unix epoch time is a scalar count of seconds since 00:00:00 UTC on 1 January 1970, the moment chosen by early Unix designers as a reference point. It's absolute — one number, one instant, no timezone ambiguity. Timezone only enters the picture when you render it as a human-readable date.

    Because it's a plain integer, it sorts correctly and does arithmetic cleanly. That's why every SQL database, every REST API's created_at, every iat in a JWT, and almost every log-line timestamp eventually boils down to epoch.

    The 1970 origin — why that date?

    Unix was created at Bell Labs in the early 1970s. When picking a zero point for timestamps, the original team chose the start of 1970 because it was recent, easy to remember, and had the round decimal property. It's arbitrary, but it stuck.

    Seconds, milliseconds, microseconds, nanoseconds

    The single most common bug in timestamp code is a unit mismatch. Here's the cheat sheet:

    UnitDigits todayTypical source
    s10Unix date +%s, Postgres EXTRACT(EPOCH FROM …)
    ms13JavaScript Date.now(), Java System.currentTimeMillis()
    μs16Postgres clock_timestamp(), Python time.time_ns() / 1000
    ns19Go time.Now().UnixNano()

    Quick rule: a 10-digit number today is almost always seconds. 13 digits is milliseconds. If in doubt, paste it into the converter — it auto-detects.

    Timezones and the wall-clock illusion

    This is where most bugs live. An epoch is timezone-independent, but the moment you format it for display you pick a zone. Same epoch, different wall-clock reads in Tokyo and São Paulo. If a user reports "the timestamp is wrong," check:

    1. What unit is the stored value? (s vs ms)
    2. What zone is the renderer using? (UTC vs browser local vs server local)
    3. Is there DST between you and the user?

    Always store epoch, never wall-clock. Render late, in whichever zone the consumer wants.

    The Year 2038 problem

    If an epoch is stored in a 32-bit signed integer, the maximum representable value is 2^31 - 1 = 2,147,483,647 seconds, which corresponds to 03:14:07 UTC on 19 January 2038. After that moment, 32-bit counters roll over to a large negative number — effectively jumping the clock back to 1901.

    In practice, most modern systems use 64-bit storage and are fine for the next ~292 billion years. But embedded devices, old databases, and stringly-typed APIs can still carry 32-bit epochs. Audit your stack now; 2038 is closer than it looks.

    Code examples

    JavaScript

    // Now (milliseconds since epoch)
const now = Date.now();

// Epoch seconds → Date
const d = new Date(epochSeconds * 1000);

// Date → epoch seconds
Math.floor(d.getTime() / 1000);

    Python

    import time
from datetime import datetime, timezone

time.time()                                             # float seconds
datetime.fromtimestamp(epoch_s, tz=timezone.utc)        # parse to aware dt
int(datetime.now(timezone.utc).timestamp())             # now as int seconds

    Java

    Instant now = Instant.now();                    // UTC instant
long epochSeconds = now.getEpochSecond();        // seconds
Instant.ofEpochSecond(epochSeconds);             // parse
ZonedDateTime.ofInstant(now, ZoneId.of("America/New_York")); // render in NYC

    Go

    now := time.Now()
epoch := now.Unix()                // seconds
nano  := now.UnixNano()            // nanoseconds
parsed := time.Unix(epoch, 0).UTC()

    SQL

    -- Postgres
SELECT EXTRACT(EPOCH FROM now())::bigint;
SELECT to_timestamp(1713484800) AT TIME ZONE 'UTC';

-- MySQL
SELECT UNIX_TIMESTAMP(NOW());
SELECT FROM_UNIXTIME(1713484800);

    Common bugs and how to avoid them

    • Off-by-1000. Multiplying by 1000 when you shouldn't (or vice versa). Always pick a unit at a system boundary and stick to it.
    • Storing local time. "2026-04-19 09:00:00" with no zone is not a timestamp. Store epoch.
    • DST math. Adding "1 day = 86400 seconds" across a DST transition yields the wrong wall clock. Use a timezone-aware library.
    • Integer overflow in JSON. JavaScript's Number can't represent 64-bit integers precisely. Nanosecond epochs must be serialized as strings.
