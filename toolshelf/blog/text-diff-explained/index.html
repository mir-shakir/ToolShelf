    How Text Diff Works: Side-by-Side vs Unified, LCS, and When to Use Each

    By The ToolShelf Team April 19, 2026 8 min read
    diff algorithm cs tooling productivity

    "Diff" is the unsung hero of software engineering. You used it five times today without thinking about it — in your code review, your git log, your config drift check. This post explains how a line-level text diff actually works, when to use each view, and where the tool surprises people.

    Want to try a diff right now? ToolShelf's Text Diff Checker runs entirely in your browser, offline.

    What a diff does

    Given two versions of a text document — call them left and right — a diff tool tells you which parts stayed the same, which were inserted, and which were deleted. The output is called an edit script, and tools render it in one of three common views.

    The three views: side-by-side, unified, inline

    Side-by-side

    Two columns, left and right, aligned so equal lines line up. Best when you want a spatial overview — "which region of the file changed?"

    Unified (a.k.a. patch view)

    One column, with each line prefixed (unchanged), + (added), or - (removed). Hunks are introduced with @@ -old_start,old_count +new_start,new_count @@. It's what git diff produces by default and what git apply / patch(1) consume. Best when you want to paste the diff into an issue, review comment, or automation.

    Inline (word-level)

    Changes highlighted inside each line — e.g. red green. Great for prose or minor line tweaks; less useful when entire blocks move. ToolShelf's current release does line-level only; inline is on the roadmap.

    LCS in plain English

    Most diff tools reduce the problem to finding the longest common subsequence (LCS) of lines between the two inputs. A "common subsequence" is any sequence of lines that appears in both files in the same relative order (not necessarily adjacent). The longest one gives you the maximum set of lines you can mark as unchanged.

    Worked example:

    left:   [a, b, c, d, e]
right:  [a, x, c, d]

LCS:    [a, c, d]        ← longest sequence in both

edit script:
  equal:  a
  delete: b
  insert: x
  equal:  c
  equal:  d
  delete: e

    Compute LCS with classic dynamic programming in O(n·m) time and space, where n and m are the line counts. Backtrack through the DP table to emit the edit script.

    Myers' improvement (briefly)

    Eugene Myers' 1986 algorithm finds the same minimal edit script in O((n+m)·D) time, where D is the edit distance. For typical source code changes D is small, so Myers is dramatically faster than plain DP. It's what git diff uses. ToolShelf's current implementation is plain LCS — simple, correct, and fast enough for interactive use up to the documented line limit.

    Ignore-whitespace traps

    Every diff tool offers an "ignore whitespace" toggle, and every team eventually gets bitten by it.

    • Collapsing internal whitespace (multiple spaces → one) usually makes diffs more readable.
    • Ignoring leading/trailing whitespace can hide genuine indentation bugs — the kind that break YAML or Python.
    • Ignoring all whitespace hides inserted newlines, which can be semantically meaningful in shell scripts and SQL.

    Rule of thumb: use ignore-whitespace for code review of someone else's diff-noise; don't use it as a permanent default.

    Use cases

    • Code review — compare a snippet against main before pushing.
    • Config drift — two servers' YAML files should match; diff proves it.
    • Document redlines — legal / spec edits, tracked without a heavy tool.
    • SQL schema comparison — two pg_dump --schema-only outputs.
    • Localization QA — source strings vs translations by line.

    Choosing the right diff tool

    Reach for git diff when the files are in a git repo. Reach for a local diff -u when scripting. Reach for a web tool when you need to paste two blocks quickly, share output with a non-engineer, or when your data is sensitive and you want it to stay in your browser. ToolShelf's Text Diff is explicitly designed for that last case — nothing leaves your device.

    Wrap-up

    Diffing looks magical, but it's dynamic programming plus a bit of rendering. Once you understand the edit script underneath, the tools' quirks (ignore-whitespace, context size, unified vs side-by-side) become easy to reason about.
